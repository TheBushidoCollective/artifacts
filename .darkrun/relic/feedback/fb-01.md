VALUE REVIEW (pre-manufacture, `frame` spec): the spec as written, executed faithfully, leaves wrong-thing risk alive in three places. Each is fixable by editing `frame-artifact`'s required content before any unit is manufactured. None of these relitigate the three locked decisions; items 1 and 3 depend on accepting them.

## 1. The single primary metric is not observable under the architecture this station locked, and the spec never says how it gets measured. (Primary defect.)

The specified primary metric is a conjunction: recipients open relics, AND opened relics are predominantly types Relic renders rather than download-only binaries.

The second conjunct requires knowing the mimetype of opened relics. Nothing in the design can produce that number:

- The server cannot know it. Zero-knowledge means the server holds ciphertext and never receives the key. `archive-browsing-and-mimetype-detection` puts mimetype sniffing "after decryption, in the browser."
- The browser cannot report it either, not with any instrument currently permitted. The sibling unit `frame-preconditions` section 4 requires that the viewing origin carry "zero third-party scripts, analytics, or error reporting, because any same-origin script can read `location.hash`."

So the observable the metric is built on has no specified path to existing. The predictable downstream outcome is that "opens, by rendered type" degrades into "opens," because opens are trivially observable (the app server mints a short-lived signed download URL at view time, per `gcs-cloud-run-architecture-constraints`). Opens alone is precisely the metric that cannot distinguish Relic from a worse file.kiwi. The instrument meant to detect the failure becomes the instrument that hides it.

Second hole in the same metric: the server sees a GET on a relic ID and cannot separate a recipient's open from the publisher's own confirmation open. Under early dogfooding by the people building it, self-opens dominate. As specified, this metric reads green in the world where Relic has zero recipients.

FIX: require `docs/frame.md` to state, alongside the primary metric, (a) the mechanism by which the type distribution of opened relics becomes observable, and what metadata that mechanism discloses to the operator, evaluated against the same document's required honesty constraint about the zero-knowledge claim; and (b) what counts as a recipient open, explicitly excluding opens the operator cannot distinguish from the publisher's own. If no mechanism survives (a), that is itself the finding, and the metric must be replaced with one this architecture can actually produce. Either outcome beats shipping an unmeasurable metric as this station's answer to "how do we know we lost."

## 2. The non-goals bound the product surface and leave the wedge itself unbounded.

Every non-goal the spec lists (accounts, dashboard, my-relics list, republish/versioning, custom domains, team features, expiry configuration, burn-after-reading) is product surface around the wedge. Rendering is the wedge and carries the entire value case, and nothing bounds it. Which types get first-class rendering is the one part of this work with genuinely unbounded scope, and it is a value question, not a shape question.

It is also urgent rather than deferrable. `archive-browsing-and-mimetype-detection` records that in-page ZIP browsing works "only if the crypto framing supports range decryption," and that "the decision is irreversible after encryption." `frame-artifact` puts the encryption wire format out of scope and hands it to `shape`. So `shape` will lock an irreversible framing decision with no signal from the frame about whether the capability it enables is inside the value case. Guessing low forecloses part of the wedge permanently. Guessing high buys range-decryptable framing to serve a capability nobody established a need for.

FIX: require the non-goals section to state which rendering capabilities are in the first release and which are out, at minimum to the granularity of whether in-page archive browsing and in-page seekable video are goals, since those two are what demand range decryption.

## 3. The value case rests on a competitor's configuration flag, and the spec does not require the frame to say so.

Both named user segments derive entirely from `claude-artifacts-capability-boundary`: they exist because Artifacts is off by default in Agent SDK, GitHub Action, and MCP-server contexts, because API-key sessions cannot publish at all, and because source types are restricted to `.html`/`.htm`/`.md`. That same recorded topic also says: "Standing risk: Anthropic can erase this opportunity by enabling Artifacts in Agent SDK and GitHub Action contexts and widening accepted file types. Both are plausible roadmap items, so anything built here should assume the window is not permanent."

The spec requires the frame to inherit every other consequence of that topic (the two segments, the explicitly ruled-out compliance segment, the 16 MiB cap, the file-type restriction) and omits this one. A frame that defines its users wholly by a gap one vendor can close unilaterally, without recording that the gap may close, has not eliminated wrong-thing risk. It has left it undocumented for a later station to discover the hard way.

FIX: require `docs/frame.md` to state the window risk explicitly where it defines the user or the value, in the recorded terms: both segments depend on a first-party gap the vendor can close, so the frame is written against a configuration that may not hold.

## What survived review

The user segments are concrete and falsifiable enough to act on, and the ruling-out of compliance-blocked orgs is a real exclusion with a stated reason. The non-goals that are present are genuine bounds, not a list of things nobody wanted: no-accounts conflicts directly with per-user abuse quotas, no-versioning concedes real ground to Artifacts, and the burn-after-reading deferral has a specific non-obvious justification (Slack unfurl and Safe Links scanners burning the relic before a human clicks). Decision 3's demotion of zero-knowledge from pitch to permission slip is the correct read of the file.kiwi evidence and the spec carries it through to the value section honestly, including the constraint that the decrypting JavaScript is served by the party the claim is made against.
