## The renderer class DOES support the opened-relics claim. Not a defect.

The concern was that a class declared at publish time might support only "published relics are predominantly renderable types" rather than "opened relics are predominantly types Relic renders." It supports the latter, and the reason is structural rather than lucky.

The class is stored against the relic ID. The open event at signed-URL mint time names the relic ID. Joining those yields the class distribution of the opened population directly. You never need to observe the class at open time; you need the class of the thing that was opened, and the ID carries that link. The attribute is also immutable for the life of the relic, because republish-to-same-URL and versioning are explicit non-goals, so one relic has exactly one plaintext and therefore exactly one true class forever. Nothing can drift between publish and open.

One honest limit, recorded so it is not mistaken for an oversight later: this measures the type of what was opened, not whether rendering succeeded. A relic declared `markdown` that fails to render still counts as renderable. Measuring render success would require a script on the viewing origin, which `frame-preconditions` section 4 forbids, so it is out of reach by design. The metric claims type and the telemetry answers type. Self-consistent, so no finding.

## Excluding opens from the publishing IP is NOT sufficient, and it fails in the direction that hides a loss. This is the finding.

Publishing-IP exclusion has two error modes and they are not symmetric.

**Publisher and recipient behind the same NAT** (same office, same VPN egress, same household): the recipient's real open is excluded as though it were the publisher's. That is a false negative. It undercounts recipient opens and makes the metric harder to pass. This direction is safe. It can only make you believe you lost when you won, never the reverse, and a metric that errs toward declaring failure is doing its job. Not worth solving.

**Publisher opening from any IP that is not the publishing IP**: phone on cellular, laptop on a VPN, a second machine, a coffee shop. The publisher's own open counts as a recipient open. That is a false positive, it inflates the exact number the metric's first clause rests on, and it hides a loss.

That second case is not a corner case for this product specifically. Relic ships a PWA, whose entire point is mobile-quality viewing. Checking a link yourself before sending it is ordinary behavior for anyone sharing a link, and "did the render come out right" is the single most likely thing a publisher of this particular service checks. The people building a PWA will open relics on phones constantly. And the period when this metric matters most is early, low volume, with the collective as publisher, which is exactly when self-checks dominate the sample.

So take the failure world the metric exists to detect: relics get published and nobody but the publisher ever looks at them. A publisher who habitually checks on a phone produces a first clause reading near 100 percent "opened by someone other than the publisher" with literally zero recipients. That is the same sentence filed in `fb-01`, unchanged. The fix moved the number without closing the hole.

Note that gate 6 cannot catch this. It checks that the document states how each half is computed, not that the stated method works. A document faithfully repeating "excluding opens originating from the publishing IP" passes gate 6 while carrying the defect.

## FIX

Naming the requirement, not the design. The framer picks the mechanism.

Require the success metric section to do three things:

1. **State that publishing-IP exclusion is asymmetric, and name both directions.** Same-NAT recipients are wrongly excluded, which is conservative and acceptable. The publisher on any other IP is wrongly counted, which hides failure. A reader of `docs/frame.md` must not come away believing the first clause is a clean number.

2. **Add at least one discriminator for the dominant false-positive case.** The publisher's self-check is overwhelmingly immediate, so a short post-publish exclusion window is the cheap option, but any mechanism that catches the publisher's own first look is acceptable.

3. **State the trust condition for the primary metric explicitly**: below what volume, or during what period, the number is not treated as informative. This is necessary because no mechanism available under the locked non-goals fully separates publisher from recipient. Accounts would do it, and accounts are a non-goal, so the residual confound is permanent and has to be documented rather than engineered away.

If the conclusion after that work is that the first clause cannot be made fully trustworthy, that is a legitimate outcome and it belongs in the document. A metric with a named, bounded confound is usable. A metric whose stated computation quietly counts the publisher as a recipient is the instrument hiding the failure it was built to detect.
