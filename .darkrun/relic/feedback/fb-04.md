COMPLETENESS REVIEW: five items fell between the four units. The decomposition is strong (I verified the four key-disclosure paths, the three couplings, and every out-of-scope hand-off; results at the end). These five are what a hand-distribution of 69 ambiguities and 78 behaviors dropped.

## 1. The fifth key-disclosure path has no owner: the key leaving via a third party

`redirects-inherit-the-fragment-and-leak-the-key` records, under "The related exposure the fragment guarantee does not cover", three cases where the key reaches some server with no Relic component misbehaving:

- Link shorteners: pasting the full URL into a shortener's form "transmits the key in a request body and stores it on that service."
- Abuse report forms (this one IS owned, `spec-service-surface` section 4).
- Enterprise link rewriters: "Microsoft Safe Links wraps URLs with the original as a query parameter; Proofpoint URL Defense encodes the original into the wrapper's path. Neither documents what it does with a fragment. If either percent-encodes the `#` into its wrapper, the key is transmitted to and logged by that vendor." The topic calls it "testable in one message by mailing a real relic through a Defender tenant and reading the delivered URL, and worth testing before launch rather than assuming."

Grep of `.darkrun/relic/units/spec-*.md`: "shortener", "rewriter", "URL Defense" appear in zero specify units. "Proofpoint" appears only in `frame-preconditions`. `spec-viewer` section 1 owns the RFC 9110 rule and enumerates six places it bites, all of them redirects Relic itself issues, then stops. `spec-service-surface` mentions Safe Links once, about `HEAD` scanning burning tokens, not about fragment handling.

So this is the same shape as the four paths the station was built around, correct components and an unspecified boundary, and it is assigned to nobody.

**Fix:** give the third-party-transit cases to `spec-viewer` alongside the redirect rule (it already owns the RFC 9110 mechanism), and give the pre-launch Defender test and the honest-claim consequence to the owner of item 2 below. The honest form the topic states is "your browser never sends the key to Relic's servers", and no unit currently carries that correction.

## 2. The published disclosure statement is pointed at by three units and specified by none

Three separate sources make it mandatory content:

- `docs/frame.md`, on the telemetry trade: "Publishers must be able to see all of it in a published privacy statement before they publish."
- `agent-mediated-key-delivery-leaks-to-the-transcript`: the transcript leak "belongs in the same published statement as the telemetry trade... A privacy statement carrying only the served-JavaScript caveat is materially incomplete."
- `redirects-inherit-the-fragment-and-leak-the-key`: the corrected key-reaches-some-server claim "Belongs in the same published statement as [the transcript leak] and the telemetry trade."

What the units actually do: `spec-publish-contract` section 4 states the transcript obligation and says it "belongs in the published privacy statement". `spec-viewer` requires a privacy-statement *link* on the pre-decryption chrome. `spec-relic-format` and `spec-service-surface` say nothing. Grep confirms "privacy statement" appears in exactly one specify unit, as a one-line pointer.

Nothing specifies the document: what it must contain, that it must be readable before publishing rather than only from a relic page, or that it must carry the retention window and the byte-lifetime arithmetic that `spec-service-surface` section 3 already derives ("any published byte-lifetime number must count TTL plus lifecycle lag plus the soft-delete window"). The frame conditions the acceptability of the telemetry trade on this document existing, and no unit writes it.

**Fix:** assign it to `spec-service-surface`, which already owns the published-policy surface, the `/abuse` URL, the SLA, and the retention window, with a completion criterion naming all four required disclosures: the telemetry trade, the agent-transcript leak, the key-reaches-some-server cases from item 1, and the published retention plus byte-lifetime numbers.

## 3. Nobody decides whether the sandbox origin is one origin or a per-relic subdomain, and PSL lead time is unrouted

`rendering-untrusted-content-origin-isolation` prescribes, for active content, "a unique cross-site domain per piece of content (`$RANDOM.exampleusercontent.com`), with the parent registered on the Public Suffix List... This isolates individual relics from each other, not just relics from the app. PSL registration is a real, slow external dependency, start it early."

`sandbox-csp-decision-and-what-the-wedge-actually-is` then writes a rule that presupposes the answer: "With per-relic subdomains the shim's expected parent origin is fixed and hardcodable, while the parent's `targetOrigin` is computed per render."

`spec-viewer` inherits the handshake and mandates "the parent replies with the payload and an **exact** `targetOrigin`" (completion criterion 11 covers the `'*'` prohibition), but never says how the parent computes that origin, because the decision it depends on is not made anywhere. Grep: "Public Suffix", "PSL", "subdomain" appear in zero specify units. `docs/preconditions.md` section 2 fixes two registrable domains, which is compatible with either answer, and section 5 lists PSL only as an unresolved Safe Browsing question, not as an isolation decision.

Consequence: `shape` takes the cheap default of one shared sandbox origin, a mandated viewer rule stays unspecifiable as written, and if per-relic subdomains turn out to be wanted, the PSL lead time was never started. Preconditions section 2 treats domain acquisition as an external dependency that blocks deployment; this one has the same character and no owner.

**Fix:** add it to `spec-viewer` section 3 as a decide-or-route item: single sandbox origin versus per-relic subdomain under a PSL-registered parent, what each buys given the sandboxed iframe already runs in an opaque origin, how the parent computes its exact `targetOrigin` under each, and route the choice to `shape` naming PSL registration as an external dependency on the same footing as domain acquisition.

## 4. There is a fourth coupling, and unlike the three it is not ordered

`spec-service-surface` section 1 decides "whether to use a machine-readable problem-detail format", naming the exact failure it prevents: "Without a stable machine-readable code, the local publishing client string-matches on human-readable prose and breaks on the first copy edit to an error message."

That local publishing client is specified in `spec-publish-contract`, which mandates that the size-rejection error "must name both the cap and the actual size, or the model retries the identical file" and the rate-limit error "must carry retry-after, or the model retries immediately and deepens the limit." Those are fields on the service's error response.

The two units run in parallel: both have `depends_on: ["spec-relic-format"]` and neither depends on the other. `spec-publish-contract` out of scope forbids it from fixing the taxonomy. `spec-service-surface` out of scope says "that sibling maps publish failures onto it", which a sibling cannot do against a taxonomy that does not exist yet.

Decided independently, `spec-service-surface` can decline the problem-detail format while `spec-publish-contract` mandates the client extract cap, actual size, and retry-after. Both units pass every gate and the result is precisely the prose-string-matching client the service unit exists to prevent. This is the same structure as the ID-entropy-before-expired-versus-404 coupling, which was ordered correctly.

**Fix:** add `spec-service-surface` to `spec-publish-contract`'s `depends_on` and its `inputs`, and fence it the way the format coupling is fenced ("the error contract is your input; do not re-decide it"). Alternatively move the machine-readable error shape wholly into `spec-publish-contract` and forbid the service unit from restating it. Ordering is the cleaner option because the taxonomy has to serve browser callers too.

## 5. `spec-viewer`'s self-declared hardest question can be deferred through its own gates

The unit says of routing `{markdown, code}` when the class cannot be trusted and the sniff is silent: "This is the hardest single question in the unit and it must be answered, not deferred."

Completion criterion 5 says "Every item in 'What this document must decide' is resolved into a stated rule **or routed to `shape`**", which permits exactly the deferral the item forbids. The unit separately routes the closely related destination question to `shape`: "whether Markdown renders on the viewing origin with raw HTML stripped or on the sandbox origin." So a writer can route the silent-sniff rule to `shape`, satisfy all twelve criteria, and leave undecided whether half the renderable wedge lands on the origin holding the fragment or on the sandbox origin.

Every other load-bearing routing rule got a dedicated criterion (6 class never routes, 7 disagreement rule, 8 SVG, 9 blob URLs, 10 redirect fragments, 11 postMessage). This one did not.

**Fix:** add a criterion requiring a stated routing rule for payloads whose sniff returns nothing, and reconcile it with the markdown-origin item routed to `shape` by requiring the rule be stated conditionally on that choice, so it is complete under either answer.
