## 1. The coupling-four fix fenced `spec-publish-contract` out of two legs the app server is structurally not in

This is a new defect, introduced by the fix.

`spec-publish-contract` criterion 11: "**Every publish failure** maps onto a status and named machine-readable fields from `docs/spec/service.md`, **with no status invented here**." Out of scope: "The status taxonomy and error format. Locked by `docs/spec/service.md`. **You map onto it; you never invent a status or a field name.**"

Its own section 1 lists the failures to cover: "size rejection, rate limit, file not found, grant expired, network failure mid-upload."

At least three of those can never have an app-server status, by this architecture's own locked rule that the ciphertext never transits the app server:

- **File not found.** The local stdio server cannot find the path on the user's filesystem. No HTTP request is made. There is no app-server status and there cannot be one.
- **Network failure mid-upload.** The client-to-GCS leg. Preconditions section 4 puts the app server outside that path deliberately, and section 3 says so again about the size cap: "the *rejection rate* is not visible to the app server, because publish uploads go direct to storage and the server isn't in that path."
- **Grant expired at the storage leg.** GCS returns its own error to the client. `service.md`'s enumerated "grant expired with no object" is a different state, an app-server record with no object, reached at mint or lookup. Mapping one onto the other is a category error.

**Size rejection is now ambiguous for the same reason.** There are two: the grant-time refusal when declared size exceeds the cap (app-server, and `service.md` enumerates it) and the upload-time refusal by the signed size constraint (GCS-side, invisible to the app server). Publish's item says the size rejection "must surface both the cap and the actual size" without saying which one, and the fence forbids it from naming a field for the GCS case.

So a writer facing criterion 11 has three choices, all bad: leave the client's two most common real-world failures unspecified, force them into server statuses that do not describe them, or violate the out-of-scope fence. And this lands on the failure publish spends its entire section 3 on, so its error surface is load-bearing rather than incidental.

**Fix:** scope both the criterion and the fence to app-server-originated failures, and give publish an explicit item owning the tool-error surface for the two legs the app server is not in. Something like: "For failures the app server never observes (local filesystem errors and the client-to-storage leg), this document defines the tool-error codes, since no server status exists and none can. State how those codes stay distinguishable from codes echoed out of `service.md`." Without that item, those failures now have no owner at all, which is the same class of gap as `fb-04`.

## 2. `spec-service-surface` did not get the criterion 5 strengthening the other three did

`grep -l 'Routing is legitimate only for items named' .darkrun/relic/units/spec-*.md` returns three files: `spec-publish-contract`, `spec-viewer`, `spec-relic-format`. Not `spec-service-surface`.

Its criterion 5 reads only: "Every item in 'What this document must decide' is resolved into a stated rule or routed to `shape`." It also dropped the original's trailing "with what `shape` must choose", so it is now weaker than it was before `fb-04`, not stronger.

Most of what this exposes is backstopped by service's own criteria: cap-exhaustion cost by 6, expired-versus-never-existed by 7, the disclosure statement by 12, third-party transit by 13, and the client-extractable error fields by 14. That last one matters most and it holds, so publish's dependency is safe.

What is left unprotected is the takedown-disclosure judgment call, the clamp-versus-overhang decision, and whether delete auto-blocklists or is a second call. The takedown one is the sharpest, because the unit itself says "**Make it, or the error handler makes it by accident**", and a writer can now route it to `shape` under the plausible cover of "the exact status codes", which *is* in service's Route-to-`shape` list. That is exactly the escape hatch fix 5 was meant to close, surviving in the one unit that now has a dependent.

**Fix:** add the same sentence to service criterion 5.

## 3. `spec-viewer`'s stub guard is set below the run's own calibrated minimum

This is the arithmetic answer to the overload question, and it is a better answer than a judgment call.

|---|---|---|---|---|
| format | 21 | 2000 | 95 | 10 |

`spec-relic-format` criterion 2 now states the run's own calibration: "**the observed rate in this run is 60 to 85 words per item**". Viewer's floor implies 58, below the bottom of that band. It is the only unit whose stub guard sits below what this run says a complete document costs, and it is simultaneously the unit carrying the most items, the most criteria, and four of the five key-disclosure paths.

Note the counting caveat honestly: format's own criterion 2 says "roughly 27 mandated items" where my method counts 21, so it counts something finer. The relative comparison is what holds, since one method was applied to all four, and the direction is unambiguous. The consequence is concrete: viewer is the one unit where a document that silently skipped several mandated items still clears its floor.

**Fix:** raise viewer's floor to sit inside its own band, roughly 2600, and say in the criterion what the number rests on the way format's criterion 2 now does.

## 5. One item was dropped in the move

The old `spec-viewer` "Already decided" list ended with: "**The telemetry decision is not license to add a viewer-side script.**" It is gone from viewer and reproduced nowhere. Grep for "license to add" and "telemetry decision" across all four spec units returns nothing; the only surviving "viewer-side script" hit is in service's "Open counts are taken at signed-URL mint time, never from a viewer-side script", which is the counting rule, not the standing prohibition.

The prohibition itself survives in viewer ("no third-party scripts, no analytics, no error reporting" plus the bundled-SDK trap), so this is not a hole in the rule. What was lost is the named future pressure that breaks it, which preconditions section 4 states directly: the two requirements "stay compatible only as long as no future station tries to satisfy a measurement question by adding a script to the viewer." That is the same "quiet violation" pattern the other units flag by name elsewhere, for instance format's note that server-side filename placement is "the most likely *quiet* frame violation in the build."

Mitigated by every unit reading `docs/preconditions.md`, so this is low, but it costs one bullet to restore and it was the only casualty of the move.

## 6. The mint success-response contract is the unfixed twin of the coupling that was fixed

Coupling four was fixed by ordering publish after service for the **error** contract. The **mint success response** has the same shape and was not ordered. `spec-viewer` mandates "the mint response carries its own expiry so the viewer can tell whether reuse is valid" and routes "whether the mint response carries object length and CRC32C" to `shape`. `spec-service-surface` owns mint placement and counting and has no item about what a successful mint returns. Viewer does not depend on service.

Risk is lower than the error case, because service has no competing item and viewer is therefore the de facto single owner, so nothing will contradict it. But it is one line to make that explicit rather than accidental.

**Fix:** add to service's out of scope: "the mint success response's contents are specified in `docs/spec/viewer.md`; do not restate them."

## Direct answers to the two questions asked

**Did fixing coupling four create a new gap?** Yes, item 1. The fence is correct in direction and too tight in extent: it assumes every publish failure is an app-server refusal, and this architecture guarantees that two whole legs are not.

**Is `spec-viewer` now overloaded?** Its scope holds and I would not split it. The six sections are one subject, the browser side, and they are genuinely interdependent in a way that would put a seam through the middle of a decision chain: section 2's origin choice determines section 4's `targetOrigin` rule and section 3's Markdown-origin decision, which determines section 6's screen copy and the copy-link affordance. Splitting security from experience would separate the Markdown-origin decision from its consequences, which is precisely the operation that produced the five gaps in `fb-04`. The load is real but it shows up as item 3, a mis-set guard, not as incoherent scope. Fix the floor, keep the unit.
