**`docs/spec/format.md` section 5 carries an overbroad redirect enumeration that its own siblings are being corrected to contradict. The unit is locked, so this is filed rather than edited.**

## What was found

`adversary-viewer` found that `spec-viewer`'s §1.7 mandates "**Every** redirect Relic issues MUST carry an explicit, possibly empty, fragment in `Location`," then lists among the places it bites "legacy or renamed paths" and "trailing-slash normalization." Both are **same-origin**.

**The manager verified the RFC directly** rather than relying on the report. RFC 9110 §17.11's remedy is scoped: "it ought to ensure that redirects **to other sites** include a (possibly empty) fragment component in order to block that inheritance." The RFC's own worked example of *desired* behavior is same-site fragment preservation.

**Applied to a same-origin redirect, the mandate destroys the key.** The server never receives the fragment, so "explicit, possibly empty" can only mean empty in practice. A recipient hitting `/{id}/#key` gets redirected to `/{id}` with an empty fragment, which blocks inheritance, and lands on the "this link is missing its key" screen. HTTP-to-HTTPS upgrade and apex-to-`www` fail identically.

`spec-viewer`'s tightener has been directed to split the enumeration: cross-site redirects get the explicit empty fragment, same-origin redirects either do not happen or deliberately omit the fragment so inheritance carries the key.

## Why this reaches `format.md`

`format.md` §5 assigns this rule to `spec-service-surface` and states it in the correct **cross-origin** form, naming service-origin-to-sandbox-origin as the case that matters. That framing is right. But its bite list includes **trailing-slash normalization**, which is same-origin, so the same overbreadth is present in a milder form: a correctly-framed rule with a counterexample inside its own enumeration.

This matters because `format.md` §5 exists precisely to be the summary downstream units inherit. A later reader taking the enumeration at face value re-derives the defect the viewer unit is being fixed for.

## Status and recommendation

**Not blocking.** `spec-viewer` and `spec-service-surface` are where the rule actually operates, and both will state it correctly. The system behaves correctly even with the stale enumeration, because no implementable rule is drawn from `format.md`'s list alone.

**Recommendation for the audit phase:** treat this as a known imperfection in a locked artifact rather than reopening the unit. `format.md` passed all four gates, went through a full Pass loop, and its section 5 framing is correct; one same-origin example inside a cross-origin list does not justify the cost of unlocking, re-running the loop, and re-recording gates. If `shape` or `build` reads `format.md` §5 in isolation and reaches for a blanket rule, the two sibling specs contradict it explicitly and win, because they own the surfaces.

**Origin note.** This is the second instance in this run of the same underlying failure: a correctly-framed rule whose stated scope and stated examples disagree. The first was `format.md` §1.1's inverted justification for having no canonicalizing redirect, which was caught and fixed during that unit's own resolve pass. Both come from applying the fragment-inheritance rule without carrying its cross-origin qualifier. Worth naming in the station reflection, because the qualifier is the part that keeps getting dropped.
