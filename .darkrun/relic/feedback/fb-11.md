**Unit:** `spec-publish-contract`. **Criterion failed:** 11 ("**Every app-server-originated failure maps onto a status and named fields from `docs/spec/service.md`, inventing no status**"). **File:** `docs/spec/publish.md` line 205 (section 3.1, "The nonce refusal is unconditional and it's needed at launch").

## The defect

`publish.md` 3.1 makes the challenge round trip unconditional and states that a grant presenting an expired nonce, or a nonce the server never issued, "**has to be refused at grant time whatever the difficulty is**" and that this "**ships in the first release**". That is an app-server-originated, launch-required refusal. It maps onto nothing in `service.md`: neither the twelve cases in 1.1 nor the three grant-time refusals in 1.6 cover it, and the Group A table at `publish.md`:122-131 has no row for it.

Verified mechanically. Every code and status pair in the Group A table was diffed against `service.md`'s 1.1 and 1.6 tables and all eight rows resolve, with zero missing field names; the nonce refusal is simply absent from the table because no code exists to put in it.

`publish.md` is correct not to invent one, per its own out-of-scope bar, and it says so plainly: "`service.md` has no code for either case today ... So this code is `service.md`'s to add." But `service.md` is a completed sibling in the same station and does not contain it, so nothing in the station's output supplies it and the gap ships.

## Why it matters, in the document's own words

`publish.md`:205 states the consequence itself: "an uncoded grant-time refusal is one the client cannot act on: 2.1's extraction rule reads `code`, so an unrecognized or absent one lands in `app_response_unusable` and the publisher gets a terminal failure where a re-challenge would have fixed it." So the specified behavior at launch is a terminal failure on a condition that is trivially recoverable, and two implementers filling the gap invent two different codes.

## Distinguish from the sibling case that is fine

The *solution* refusal at `publish.md`:203 is correctly handled and is not part of this finding: it is conditional on a non-zero difficulty, which is routed to `shape` at section 6 item 2, and item 2 names the new `service.md` code as a consequence of that pick. That one is gated behind a routed decision. The *nonce* refusal is not gated behind anything; the document makes it unconditional and launch-required.

## Mechanism, for the fix

`git log` ordering: `4a9507c`/`e6ebc99` (publish.md) landed after `ed51b43` (service.md's final content commit). `service.md` was finalized before the challenge round trip existed, so it never had the chance to carry the code. This is the same root cause as fb-10: an obligation assigned to `service.md` by a document written after `service.md` was done.

## What would make it pass

Either is acceptable:

1. **Add the code to `service.md`.** One row in its 1.6 table for a grant presenting an expired or unissued challenge nonce, with a status and a bare `code` token, carrying `retry_after_seconds` if the correct client action is to re-challenge. Then add the matching row to `publish.md`'s Group A table at line 122 with its named fields, and update 3.1 to consume it instead of flagging it as missing.
2. **Fold it into an existing `service.md` code.** If the intent is that an expired or unissued nonce is a client defect rather than a retryable state, say in `publish.md` 3.1 that it maps onto an existing 1.1 or 1.6 code and add that row to Group A. This needs no change to `service.md` but must name the code explicitly rather than leaving the reader to pick one.

Option 1 matches what `publish.md` 3.1 already argues for, since it says a re-challenge is the correct remedy and a terminal failure is the wrong outcome.
