## A launch-required grant-time refusal has no code anywhere in the four documents

**Unit:** `spec-publish-contract`. **Criterion:** 11 ("Every app-server-originated failure maps onto a status and named fields from `docs/spec/service.md`, inventing no status"), with criterion 5 secondary.

**File and line:** `docs/spec/publish.md` line 205, section 3.1. Counterpart gap: `docs/spec/service.md`, which contains **zero** occurrences of "challenge", "nonce", or "proof of work" (verified by grep across the whole file).

### The gap

`publish.md` section 3.1 introduces a three-message flow whose first message is a challenge, and makes that round trip **unconditional and shipping in the first release** (line 197: "Delete proof of work from the design entirely and the round trip still ships, unchanged"). Line 205 then states the consequence:

> **The nonce refusal is unconditional and it's needed at launch.** The challenge carries an expiry, so a grant presenting an expired nonce, or a nonce the server never issued, has to be refused at grant time whatever the difficulty is. [...] `service.md` has no code for either case today, and an uncoded grant-time refusal is one the client cannot act on: 2.1's extraction rule reads `code`, so an unrecognized or absent one lands in `app_response_unusable` and the publisher gets a terminal failure where a re-challenge would have fixed it. So this code is `service.md`'s to add [...] and it ships in the first release rather than waiting on a difficulty value.

`service.md` does not have it. Its section 1.6 added three grant-time refusals for this sibling (`invalid_relic_id`, `relic_id_collision`, `relic_not_yet_published`) and none covers a nonce. Case 12's `invalid_publish_metadata` is scoped to renderer class and client name. The challenge endpoint's own refusals named at `publish.md` line 207 (`429 publish_rate_limited`, `503 service_paused`) are refusals of the challenge request, not of a grant presenting a stale nonce.

### Why this is a criterion failure

Criterion 11 requires every app-server-originated failure to map onto a status and named fields from `service.md`. This one is app-server-originated, ships at launch by the document's own statement, and maps onto nothing. `publish.md` is correct not to invent the code, since its "Out of scope" bars it from inventing app-server statuses, so the failure is in the set rather than in the document's judgment. But the criterion is not satisfied, and the consequence is concrete and stated by `publish.md` itself: under the set as written, an expired challenge nonce falls to `app_response_unusable`, which `publish.md` 2.2 and 4.6 make **terminal and never retried**, so a publisher whose challenge simply timed out gets a permanent failure where re-challenging would have worked.

Criterion 5 is the secondary hook: the code is routed to a sibling rather than to `shape`, and routing is legitimate only to `shape` and only for items on the unit's own Route-to-`shape` list. Route item 2 covers only the *solution* code and only **conditionally**, on non-zero difficulty ("Once picked, if difficulty is non-zero"). The nonce refusal is unconditional, so nothing in either document's route list carries it. `shape` inherits a hole rather than a decision.

### What would make it pass

`service.md` section 1.6 gains one row for a grant presenting an invalid or expired challenge nonce, with a stable `code` in the same shape as the other three, and `publish.md` section 2.1's Group A table gains the matching row so the client can key a re-challenge on it rather than terminating. The status value and code token are the spec's to fix here, not `shape`'s, on the same reasoning `service.md` 1.6 already used for `relic_id_collision`: the client has a correct recovery action, so it needs something matchable to hang it on. Note the recovery differs from a retry, so whatever code is chosen should be excluded from `publish.md` 4.6's retry set and routed to a fresh challenge instead.

If instead the station decides the challenge should not ship unvalidated in the first release, that closes it too, but `publish.md` 3.1 argues against a conditional round trip and that argument would need reopening.
