FIT-5. `design-product-surface` and `design-operations-and-abuse` run in parallel with overlapping charters on two surfaces, and neither out-of-scope line excludes the other.

Both units sit in the final wave. Surface depends on container and topology; operations depends on storage and topology. There is no edge between them, so neither reads the other's output. Their boundaries overlap in three places:

**1. Recipient-facing screens.** `design-operations-and-abuse` §5 is told: "**Cap exhaustion and takedown are the same experience for a recipient.** Both return the same status... **Decide whether the viewer distinguishes them**, and note the support-load consequence either way." That is a viewer screen decision. `design-product-surface`'s stated goal is "every recipient-facing state including the ones nobody has written," and its criterion 7 requires all three missing states specified with copy. Operations' out-of-scope line excludes "art direction," which is narrower than viewer screens and does not exclude this. Surface's out-of-scope line excludes "Abuse operations and legal posture," which does not obviously cover a cap-exhaustion screen either. Each unit can reasonably assume the other owns it. Worse, the context is split the wrong way: operations reads `service.md` §§1.4, 4, 4.1, 5, 6 and therefore holds §1.2 cap exhaustion and §1.4 takedown disclosure, while surface reads `service.md` §§2, 4.1, 5 and never reads §1 at all. So the unit that owns the screens cannot see the status taxonomy the screen is about.

**2. The abuse taxonomy.** Surface §3 is told to "decide whether the abuse taxonomy needs a **personal-data category**," while surface's own out-of-scope line assigns "Abuse operations and legal posture" to operations, and operations §2 designs the intake-to-resolution pipeline end to end against the same `service.md` §4.1 abuse form. Surface's body contradicts its own boundary, and operations is the unit that will actually process the category.

**3. Disclosure.** Operations §5 is told to "decide where this is disclosed" for cross-relic correlation. Surface §5 owns the publishing moment and the MCP sentence. Both point at `service.md` §5's published disclosure statement, which both units read. Two documents can write conflicting content into the same statement.

This is the failure `specify` shipped twice, and the station spec's process carry-forward addresses only half of it: "no unit in this station assigns an obligation to a sibling." All five units carry that instruction. None of them prevents two units from *silently deciding the same thing*, which is what happens when two parallel units are each told to decide a viewer screen and neither is told the other was.

**What would make this pass:** pick one owner per surface and say so in both units' out-of-scope lines. The natural split is surface owns every recipient-facing screen and its copy, including the cap-exhaustion-versus-takedown distinction and the personal-data category's user-facing label, with operations owning the pipeline behind it and the disclosure statement's legal content. Then either add an edge so the second unit reads the first, or state the need in the standard form this station already uses ("state the need and the behaviour that follows from it, and name the sibling that owns the decision"). Surface also needs `service.md` §1 added to its read list; it cannot write copy for statuses it never reads.
